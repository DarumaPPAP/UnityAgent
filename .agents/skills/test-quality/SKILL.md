# テスト品質

振る舞い・不変条件を単位に、誤実装を検出でき、失敗理由を説明できるテストを設計する。拒否系の適用境界では、正しい拒否結果と、禁止された副作用の不在を一組で確認する。

## 適用範囲

PythonとUnity C#に共通適用する。対象Projectの規約、Framework、Version、既存API・テストを確認し、それらに合わせる。例示のAPIを製品に存在するものと解釈しない。

設計相談・レビューではファイルを変更しない。実装依頼でも、製品の公開API・承認契約・依頼範囲を、このSkillを理由に拡張しない。

UnityAgentの恒久採用・廃止・一時Probe・Cleanupの運用は、既存の `test-lifecycle` に従う。このSkillはテスト内容の品質を扱い、新しい承認機構や実行基盤を定義しない。

## ケースの責務を定める

次の内容を、既存の仕様・コード・テストから確認する。明確に読み取れる場合は、別書式への転記を求めない。

| 観点 | 確認する内容 |
| --- | --- |
| 契約 | 条件、操作、期待結果と、その仕様上の根拠 |
| Failure | このテストが失敗すべき具体的な誤実装 |
| 範囲 | 通す入口、実依存・代替依存、検証対象外の境界 |
| 副作用 | 禁止する変更と、監査記録など許可・要求される変更 |
| Fixture | 必要な前提、可変状態、資源の所有者と解放方法 |

一つのテストでは、一つの振る舞い・不変条件を確認する。Assert数、テスト数、行数、ファイル数そのものを品質基準にしない。

## Assertion：判断と適用の責務を分ける

| 責務 | 実際に通す処理と主な確認 | 差し替えられる部分 |
| --- | --- | --- |
| 判定 | 実Verifierの受理・拒否と、契約に含まれる拒否理由 | 判定対象外の依存 |
| 適用境界 | 実Verifierから適用処理への接続、実行抑止・保護対象・必要な監査 | 検証対象外の外部サービスや変更Backend |
| 呼び出し側の応答 | 応答を受けた側の表示・状態・後続処理 | Verifierの応答を指定するStub |

この分類は該当する責務へ適用する。すべての機能に三種類のテストやVerifier層を追加するものではない。

単独の拒否条件を確認するケースでは、それ以外の前提を成立させる。別の条件による先行拒否でも通るケースにしない。複数条件が不正な場合の拒否理由の優先順位が契約にある場合は、その組合せを判定テストで確認する。

判定テストへ、呼び出し側が担当するDispatch抑止やファイルの無変更を一律に重複させない。適用境界では、その境界が保護する対象と属性を直接観測する。DispatchのSpyだけで、別経路の書込みまで否定しない。

期待値は仕様・契約・独立に確認した具体例から定める。検証対象と同じ計算式のコピーや、実行結果の無審査な正解化を避ける。契約に必要な項目を具体的にAssertし、無関係な内部フィールドまで固定しない。

拒否系だけでは「常に拒否する」誤実装を検出できない。対応する正常系で受理と必要な処理を確認する。既存テストがその役割を満たす場合は再利用する。

## Mock・Stub・Spy：対象の外側を差し替える

Test Doubleを使う前に、検証する判断・状態遷移・接続を特定する。その処理自体を差し替え、設定した戻り値を確認するだけのテストにしない。

呼び出し側の応答テストでは、Stubに設定した値そのものではなく、その応答によって生じる表示・状態・後続処理を確認する。実Verifierの判定や接続を確認したとは報告しない。

呼出し禁止・引数・回数・順序が契約なら、SpyやMockで確認する。内部Helperの呼出し順など、契約ではない実装詳細は固定しない。

実FSへの保存、OSのLock、Unity Lifecycleなど、境界自体が検証対象の場合は、Test Doubleだけでその成功を主張しない。監査の永続保存が契約なら、保存を担当する境界で実際の保存と読み戻しを確認する。

ライブラリ上の名称より、Test Doubleが担う役割を重視する。既存の差替点を優先し、差替えのためだけにInterface・Factory・共通基底クラスを追加しない。

## Fixture：資源管理を共通化し、前提を見える場所に置く

Fixtureは、必要な最小限の状態で構成する。各ケースを単独実行できるようにし、前のテストやユーザーの作業状態へ依存させない。

| 配置 | 内容 |
| --- | --- |
| 共通化できる部分 | 一時領域、生成物の登録・解放、同じ責務で使う最小限の構築手順 |
| ケース内に残す部分 | 検証条件、境界値、意図した不正状態、意味のある初期値、期待結果 |
| ケースごとに独立させる部分 | 変更されるファイル・Object、呼出し記録・監査記録などの可変状態 |
| 共有できる部分 | ケースから変更されないデータ。変更時はケース所有のコピーを使う |

Helperを使っても、ケースの意味を決める値は呼出し側へ明示する。条件を隠す既定値、多数のフラグによる切替、異なる責務をまとめた巨大Fixtureを避ける。

前提を保証する既存の生成処理や型を再利用する。保証できない前提は必要な方法で確認し、検証対象自身の結果で前提確認を代用しない。

代表的な正常E2Eでは、到達可能な状態を使う。拒否・改竄・破損では、狙った不正状態をテスト所有データとして作る。保存済みFixtureは対象Versionと必要な不変条件を確認し、実行時に原本を変更しない。

Resource確保後は、後続の準備・実行・Assertionが失敗しても解放される構造にする。削除・破棄するのは、そのテストが生成・所有した対象だけとする。ユーザーの既存Scene・未保存状態・AssetをFixture都合で保存・変更・閉鎖・削除しない。

共有状態を変更した場合は、変更前の値を復元する。未完了処理を後続ケースへ漏らさず、Cancel・失敗時にも必要な停止と解放を行う。

## 肥大化と冗長な命名を防ぐ（Common mistakes）

適用境界へ判定条件の全入力表を複製せず、接続上の異なるFailureを守るケースを選ぶ。同じ入力が複数のテストに登場することだけで重複と判断せず、追加で検出する不具合を説明できるか確認する。

同じ責務は既存のTest Moduleへまとめる。Fixture・実行環境・所有者・失敗原因の独立性を根拠に分割し、分類ごとに機械的にファイルを増やさない。

短く読める準備は直接書き、実在する重複や保守上の問題がある部分だけ共通化する。Helperを何段も追う、フラグを解読する、無関係なケースまで変更が波及する場合は、共通化の範囲を見直す。

名前は、namespace・クラス・周囲のコードから分かる情報を重複させない。ケースを識別するために必要な条件・結果を示し、全Assertionや処理手順を名前へ列挙しない。短さのために責務を曖昧にもしない。対象Projectの命名規約に従う。

## 検証と報告（Output contract）

不具合修正では、意図した理由での修正前FAILと修正後PASSを確認する。追加テストが既存コードで直ちにPASSした場合は、その事実を記録する。検出力の証拠が必要なら、隔離した一時コピーへの故障注入や既知の不具合Revisionを使い、実行不能や無関係な失敗を検出成功に数えない。

非同期処理は、対象の完了条件と待機上限を定める。固定sleepや成功するまでのRetryで不安定さを隠さない。

結果は「保護契約／指摘または変更／実行した検証／未観測の境界」を示す。Static、Python、Unity Compile、Editor、Player、実機、Visual、Performanceを区別し、未実行・Skip・環境不備をPASSへ変換しない。観測した対象・属性・時間範囲を超えて成功を主張しない。

カバレッジは未実行領域を探す補助指標として使い、数値だけで品質や削除可否を決めない。AI探索・Visual判定の確率的な品質指標・合否閾値は、別途設計する。

## 最終確認（Checklist）

- [ ] 検証する契約と、実依存・代替依存の範囲が一致している。
- [ ] ケース固有の前提が読み取れ、Fixtureの所有と解放が明確である。
- [ ] 検証結果と未観測範囲を区別し、追加ケースの検出価値を説明できる。
